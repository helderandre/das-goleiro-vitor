Mercado Pago e Melhor Envio: como ligar pagamento e frete ao ecommerce e ao dashboard

Frete cotado no Melhor Envio antes do pagamento, cobrança no Mercado Pago com produto + frete, confirmação por webhook, etiqueta e rastreio gerados pelo dashboard — e os caminhos de pedido manual, cancelamento e reembolso.

Veredito

As duas integrações são viáveis. O que bloqueia não é a API — é o que falta no projeto e na conta do cliente.

Mercado Pago
Checkout Pro

Preferência + redirect. Sem PCI, cobre Pix, cartão, boleto e saldo MP. O mesmo link (init_point) serve para cobrar pedidos criados no dashboard. SDK Node testado rodando em Cloudflare Workers.

Melhor Envio
Viável, via aplicativo OAuth

Cotação, etiqueta, rastreio e webhooks existem e estão documentados. Exige app OAuth (não token do painel) para receber webhooks, saldo na Melhor Carteira e conta verificada.

Bloqueio técnico
Schema e site

Produtos não têm peso/dimensões; o pedido não guarda frete, CPF nem telefone do destinatário; não há tabela de eventos. O site público precisa mudar antes de qualquer etiqueta.

Bloqueio de negócio
3 respostas do cliente

Regime fiscal do remetente (NF-e ou declaração de conteúdo), quem será o titular PF da conta Melhor Envio, e KYC concluído na conta Mercado Pago.

Decisões que a pesquisa fecha

  • Frete entra como item da preferência (“Frete – PAC”), nunca em shipments.cost: a referência diz que shipments.mode: custom “não está disponível para Checkout Pro”.
  • Um único receptor de webhooks, no dashboard (Cloudflare Workers, service role do Supabase). A notification_url da preferência tem prioridade sobre o painel — site e dashboard devem apontar para a mesma URL.
  • “Link de pagamento” do painel do MP não é integrável: não tem API nem webhooks. O equivalente programático é a preferência do Checkout Pro.
  • Melhor Envio por aplicativo OAuth, não token pessoal: webhooks só disparam para etiquetas geradas pelo mesmo app; token pessoal não tem refresh nem webhook.
  • Total sempre recalculado no servidor: o site grava pedidos com anon key, então orders.total hoje é editável pelo cliente. A preferência precisa nascer de products + re-cotação do frete.
  • Manter os 5 status atuais do pedido (contrato do site) e adicionar payment_status e shipment_status separados, em vez de inflar o enum.
  • Estoque reservado na criação do pedido com UPDATE … WHERE stock >= qty numa função Postgres, liberado em cancelamento/expiração — não no “pago”.

Onde o projeto está hoje

Este repositório é só o dashboard admin. O site público (loja) é outro projeto Next.js, não disponível nesta máquina, que grava no mesmo Supabase. Nada de Mercado Pago ou Melhor Envio foi implementado em nenhum dos dois; o único vestígio é a coluna orders.mp_preference_id, exibida como texto.

Pedidos
Criados exclusivamente pelo site, com anon key + RLS. O dashboard só faz SELECT/UPDATE (app/(dashboard)/pedidos/actions.ts). Não existe criação manual.
Pagamento
Admin sobe comprovante (bucket payment-proofs) e troca o status na mão. Sem validação de transição; status é texto livre duplicado em 6 arquivos.
Frete
tracking_code é campo de texto; o site monta link para linkcorreios. products não tem peso nem dimensões.
Infra
Next 16 + OpenNext em Workers (nodejs_compat, compatibility_date 2025-04-01). Não existe app/api; o middleware de auth cobre todas as rotas — um webhook seria redirecionado para /login.
Segredos
Só NEXT_PUBLIC_SUPABASE_* via process.env. Sem service role, sem .env; o .gitignore ignora apenas .env*.local.
Deploy
wrangler versions upload — publica versão sem ativar; Cron Triggers só entram com wrangler triggers deploy.

SDK Node mercadopago no Cloudflare Workers testado

Versão 3.6.0, sem dependências, usa fetch global. Um Worker com a mesma config do repo (nodejs_compat, compatibility_date 2025-04-01) carregou o SDK, chegou à API e validou assinatura. Exigir >= 3.3.0 (correções no validador de webhook). Importar só em código server-only — nunca no middleware, que roda no wrapper edge. Alternativa igualmente viável: wrapper fetch de ~80 linhas. Detalhe do SDK: requestOptions vazam para a instância de MercadoPagoConfig — criar uma instância por request.

Webhook: algoritmo e regras

Tópico payment é obrigatório; topic_merchant_order_wh, topic_chargebacks_wh, topic_claims_integration_wh e stop_delivery_op_wh (fraude, sem retry) são úteis. IPN está sendo descontinuado e não valida assinatura — ignorar.

// manifest — data.id vem da QUERY STRING, não do body
const dataId = url.searchParams.get("data.id") ?? "";
const [ts, v1] = parse(req.headers.get("x-signature")); // "ts=…,v1=…"
const manifest = [
  dataId && `id:${dataId}`,          // minúsculas se alfanumérico (doc); SDK usa caixa original — tentar ambos
  xRequestId && `request-id:${xRequestId}`,
  `ts:${ts}`,
].filter(Boolean).join(";") + ";";    // o ';' final é o erro mais comum
const expected = hex(HMAC_SHA256(MP_WEBHOOK_SECRET, manifest));
timingSafeEqual(expected, v1);        // comparar byteLength antes
  • Payload não traz status. Sempre GET /v1/payments/{id} e decidir pelo status retornado; action serve só para log.
  • 200/201 em < 22 s, senão reenvio em 15 min, 30 min, 6 h, 48 h, 96 h ×3. Sem garantia de ordem nem deduplicação: idempotência por (data.id, x-request-id) e transições monotônicas (nunca regredir paid → pending).
  • ts está em milissegundos na doc; o toleranceSeconds do SDK assume segundos e rejeitaria tudo — não usar; implementar anti-replay próprio (|now − ts| > 5 min → rejeitar).
  • Testes: pagamentos com credenciais de teste via notification_url não notificam. Usar a “URL de teste” do painel e o botão Simular (envia live_mode: false e um Data ID arbitrário → tratar 404 do GET como “ignorar e responder 200”).
  • Responder e processar depois: no Workers, getCloudflareContext().ctx.waitUntil() estende até 30 s após a resposta. Gravar o evento antes de responder; reprocessar processed_at IS NULL por cron.

Pedido criado no dashboard

Mesma preferência do Checkout Pro, com payer pré-preenchido (nome, e-mail, CPF, telefone), expires de 3–7 dias e external_reference = orders.id. O admin copia o init_point e envia por WhatsApp/e-mail; o webhook confirma como qualquer outro pedido. Para “cliente na frente do admin pagando por Pix agora”, a Orders API devolve qr_code, qr_code_base64 e ticket_url (validade padrão 24 h, entre 30 min e 30 dias) exigindo só payer.email + external_reference — sem CPF.

Credenciais, testes e tarifas

Conta e aplicação

  • Uma aplicação (“Pagamentos online → loja própria → Checkout Pro”). Credenciais de teste vêm prontas; produção exige ativar com indústria + URL e identidade validada — senão a preferência falha com collector_does_not_comply_with_current_regulation.
  • Token de teste também começa com APP_USR-: não detectar ambiente por prefixo; usar live_mode.
  • Não há host de sandbox: mesma api.mercadopago.com. sandbox_init_point está marcado “não utilize”.
  • Segredos: MP_ACCESS_TOKEN e MP_WEBHOOK_SECRET só no Worker. OAuth não é necessário (vendedor único).
  • Compartilhar credenciais com a conta Mube (até 10 compartilhamentos) em vez de pedir login do cliente.

Testes

  • Comprador de teste em aba anônima; cartões de teste com titular APRO / CONT / OTHE e CPF 12345678909.
  • Pix e boleto nunca aprovam em sandbox no Checkout Pro — ficam pending. O fluxo “pago por Pix” só se valida com o simulador do painel ou uma venda real de valor baixo.
  • “Qualidade da integração” (mínimo 73 pontos) só roda com um pagamento de produção.

Melhor Envio

Melhor Envio: viabilidade confirmada, com condições

API v2 em https://melhorenvio.com.br/api/v2 (sandbox em sandbox.melhorenvio.com.br). Sem SDK oficial JS — só PHP; um wrapper fetch resolve. Todas as chamadas exigem Authorization: Bearer, Accept/Content-Type: application/json e User-Agent: "Goleiro Vitor Loja (email)". O runtime real do Workers não envia User-Agent por padrão (o Miniflare envia): funciona em dev e falha em produção se não for setado explicitamente.

Conta e carteira — condições operacionais
  • Conta de produção é obrigatoriamente pessoa física (CPF + selfie com documento); o CNPJ da loja entra como “Loja” vinculada com endereço principal. Definir o titular.
  • O checkout da etiqueta debita a Melhor Carteira; sem saldo a compra falha (erro não documentado). Saldo via Pix/boleto no painel ou POST /me/balance. Repesagem gera débito e pode bloquear novas etiquetas.
  • Limite de envios simultâneos: 3 etiquetas geradas e não postadas sem verificação de conta; até 50 verificada. A conta precisa passar pela verificação antes de operar.
  • Transportadoras precisam ser habilitadas por aplicativo no painel (Integrações → Catálogo → Aplicativos Autorizados → Transportadoras e Serviços), senão a cotação volta vazia.

Cotação — POST /api/v2/me/shipment/calculate

  • Payload: from.postal_code, to.postal_code, products[] {id, width, height, length (cm inteiros), weight (kg), insurance_value (2 casas), quantity ≤ 100} — o ME empacota e devolve packages[]. Alternativa volumes[] (campo de seguro é insurance). Nunca os dois juntos. services: "1,2,17" opcional; omitir deixa o painel do app decidir.
  • Resposta: array, 1 item por serviço; preços como string; usar custom_price/custom_delivery_range (refletem acréscimos do painel); prazo em dias úteis sem contar a postagem. Serviço indisponível vem no mesmo array com error e sem price — filtrar.
  • IDs: Correios 1 PAC, 2 SEDEX, 17 Mini Envios; Jadlog 3 .Package, 4 .Com, 27 Centralizado. Nunca validar por nome. Sandbox só tem Correios e Jadlog.
  • Restrições Correios (API): caixa mínima 11 × 2 × 16 cm, máx 105 cm/lado, soma ≤ 200, 30 kg. Mini Envios ≤ 300 g, ≤ 24 × 16 × 2 cm, seguro ≤ R$ 100. Um livro fino cabe em Mini Envios; padronizar dimensões mínimas no cadastro.
  • Correios, J&T, Loggi e Jadlog Centralizado não aceitam múltiplos volumes: se packages.length > 1, são n inserções no carrinho (o plugin oficial simplesmente oculta cotações Correios com ≥ 2 pacotes).
  • Sem TTL de cotação documentado. Tabelas dos Correios mudam; o preço só congela ao inserir no carrinho. Daí: re-cotar no checkout e comparar cart.price com shipping_cost após o pagamento — diferença para cima vira needs_attention.

Fiscal: NF-e ou Declaração de Conteúdo?

Envio comercial exige options.invoice.key (chave NF-e de 44 dígitos) e IE do remetente. Envio não comercial (non_commercial: true, sem invoice, state_register vazio/“ISENTO”) só é permitido a pessoa física ou PJ não contribuinte de ICMS; MEI que vende deve emitir NF-e. Livros têm imunidade tributária, mas a obrigação acessória continua. Sem essa resposta o POST /me/cart não pode ser implementado corretamente — e, se for NF-e, o dashboard precisa de um emissor integrado.

Prazos de validade da etiqueta docs divergem

FAQ da API: 20 dias para pagar, 20 para gerar, 20 para postar (7 nos Correios). Central de Ajuda e guia de compra: 7 + 7 + 7 dias corridos. Projetar para 7 dias: inserir no carrinho só após paid, alertar o admin em D+5 de etiqueta gerada e não postada, tratar expired_at/order.cancelled como terminal (crédito na carteira precisa de conferência manual — a doc não afirma estorno automático na expiração).

Webhook (painel do app → “Novo Webhook”)

  • Eventos: order.created / pending / released / generated / received / posted / delivered / cancelled / undelivered / paused / suspended. Só transições da etiqueta — não há eventos de movimentação da transportadora.
  • Header X-ME-Signature = base64(HMAC-SHA256(corpo bruto, Secret do app)). Ler request.text() antes de qualquer parse; aceitar hex como fallback.
  • Timeout 6 s, 5 tentativas a cada 15 min, depois descarta. Responder 200 antes de processar.
  • Payload traz tracking, self_tracking, tags, timestamps e tracking_url pronto — salvar esse campo (o exemplo da doc tem um typo com espaço).
  • Ao cadastrar, o ME faz uma requisição de teste; 403 (Bot Fight Mode, Access) gera E-WBH-0002. Rota pública, fora do middleware.
  • Sandbox avança status a cada 15 min até entregue — permite testar o handler ponta a ponta.

Polling de segurança — POST /me/shipment/tracking

  • Aceita vários UUIDs por chamada; devolve status + tracking (transportadora, pode chegar até 1 dia útil após a postagem) + melhorenvio_tracking.
  • Cache de ~1 h segundo a equipe do ME (2021) — polling a cada 2 h em lote é suficiente e fica muito abaixo de 250 req/min.
  • Cobre: código que chega depois do order.posted (não há evento para isso), etiquetas geradas fora do app, webhooks que falharam 5×.
  • Código exibido = coalesce(tracking, self_tracking, tracking_code manual); link https://www.melhorrastreio.com.br/rastreio/{codigo}. Melhor Rastreio não cobre J&T.
  • Se to.email for preenchido, o Melhor Rastreio envia e-mails de movimentação ao cliente (padrão ligado; desligar em Gerenciar → Configurações se a loja já notificar).

Contrato com a loja

Mudanças necessárias no site público

O site precisa mudar antes de o fluxo de etiqueta ser ativado — pedidos pagos sem CPF/telefone ficam presos até o admin contatar o cliente.

  • Checkout coleta CPF, telefone, e-mail e nome do destinatário em pedidos com item físico; não pedir CPF em pedidos só de e-book nem para Pix.
  • Cotação de frete por CEP chamada no servidor (token do ME nunca no browser), com cache de 15 min e debounce; exibir serviço, preço e “X a Y dias úteis”.
  • Criação do pedido via rpc('create_order') em vez de inserts diretos; o servidor re-cota, congela a cotação e recalcula o total.
  • Preferência do MP criada no servidor e redirect para init_point; página de retorno lê a query (status, payment_id, external_reference) e mostra “aguardando confirmação” para Pix/boleto.
  • Liberação do e-book só quando orders.status = paid (via RLS do próprio pedido), nunca pelo redirect.
  • Página do pedido: status derivado, código de rastreio (transportadora ou ME), link do Melhor Rastreio, aviso “código pode levar até 1 dia útil” quando postado sem código. Substituir o link do linkcorreios.
  • Os 5 status atuais continuam válidos; o site pode opcionalmente ler payment_status/shipment_status para mensagens mais precisas.

Alternativa arquitetural: concentrar cotação + criação de pedido + preferência em rotas do dashboard chamadas pela loja (um só lugar com a lógica de total e os clients MP/ME), evitando duplicar código entre dois repositórios sem pacote compartilhado.

Runtime

Cloudflare Workers e Supabase: o que precisa mudar no dashboard

Rotas e middleware

  • Criar app/api/webhooks/mercadopago/route.ts, app/api/webhooks/melhor-envio/route.ts e app/api/jobs/*; ler await request.text() uma vez, query via request.nextUrl.searchParams.
  • Excluir do matcher: '/((?!api/webhooks|api/jobs|_next/static|_next/image|favicon.ico|.*\\.(?:svg|png|jpg|jpeg|gif|webp)$).*)'.
  • Não migrar middleware.ts para proxy.ts: o OpenNext ainda não suporta (issue #962 aberta). Manter o wrapper edge; não importar SDK do MP nem APIs Node no middleware.
  • Server actions de pedidos não checam role — adicionar requireAdmin() em cada uma antes de expor rotas sem middleware.

Segredos

  • npx wrangler secret put: MP_ACCESS_TOKEN, MP_WEBHOOK_SECRET, ME_CLIENT_ID, ME_CLIENT_SECRET, SUPABASE_SERVICE_ROLE_KEY, JOB_SECRET. process.env já funciona (flag nodejs_compat_populate_process_env ativa desde 2025-04-01).
  • Corrigir .gitignore (.env, .env.*, .dev.vars*) antes de criar qualquer credencial local.
  • Criar lib/supabase/admin.ts (service role, persistSession: false) usado só em webhooks/jobs.

Agendamento

  • O worker gerado pelo OpenNext só exporta fetch. Opção A: custom worker que reexporta o fetch e adiciona scheduled + triggers.crons. Opção B (mais simples): pg_cron + pg_net no Supabase chamando /api/jobs/sync-tracking, /api/jobs/reconcile-payments, /api/jobs/refresh-me-token com header x-job-secret.
  • Com a opção A, o pipeline atual (wrangler versions upload) não ativa crons — precisa de wrangler triggers deploy.
  • Jobs: rastreio a cada 2 h; expiração de preferências/estoque a cada 15–30 min; refresh do token ME quando faltar < 7 dias; reprocessar eventos com processed_at IS NULL.

Plano e proteção

  • Workers Free tem 10 ms de CPU por requisição — validar HMAC + GET no MP + escritas no Supabase pode estourar. Plano Paid (30 s CPU, 10k subrequests) é praticamente obrigatório para webhooks e jobs. waitUntil é cancelado após 30 s.
  • Bot Fight Mode na zona do dashboard pode desafiar os POSTs do MP/ME e não é contornável por regra WAF — usar zona sem BFM ou Super Bot Fight Mode com exceção.
  • Subir compatibility_date para ≥ 2025-09-15 por robustez do polyfill de process usado pelo SDK do MP.
